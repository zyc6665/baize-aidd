# 事件综述与后续判断的评测

事件页顶部的综述由 `industry/prompts/story-digest.md` 生成：100–300 字、1–3 段，第一句讲清核心变化和当前结论，标题不超过 30 字。有新报道时它是对上一版的增量改写——要把「这次新发生了什么」和「之前已经说过什么」分开，读者才看得出后续。改提示词前，在同一批事件上把现有版本和候选版本并排跑一遍，人工比较；不要凭页面印象判断。

## 1. 准备案例

```bash
node --env-file=.env scripts/eval-story-digests.ts --stories <事件id>,<事件id> --out .data/story-digest-cases.jsonl
```

事件 id 是事件页地址 `/story/<id>` 里的那一段（uuid）。导出只读数据库，不调用模型，也不改动任何事件：报道按站点生成综述时的同一套规则取（只取这个事件事实对应的、已公开且已到发布时间的报道，撤下的和还没公开的不算）。已有综述的事件按「更正后重写」组装（不带上一版综述），还没有综述的按首次撰写。找不到、已被合并或没有可用报道的事件会直接报错。

导出的文件每行一个事件，可以先审阅再改。`inputMode` 有两种：

- `"incremental"`（默认）：有 `story.previousDigest` 时按增量更新组装，`knownArticleIds` 里的报道算上一版已经写过，其余标成新进展；两者都没有就是首次撰写。想测「有新报道时判断得对不对」，填上一版综述和已包含的报道 id，`reports` 放这个事件现在的全部报道。
- `"corrected"`：按更正后重写组装，带全部报道、不带上一版综述。导出时如果事件已经有综述，用的就是这个模式。

也可以手写案例，字段见 `industry/story-digest-eval.example.jsonl`（虚构示例）：每条报道带 `id`、`publishedAt`、`source`、`firstParty`、`title`、`summary`，以及结构化事实 `fact`（`subject`、`action`、`object`、`conditions`、`evidence`，其中 `structured.conditions[].quote` 是原文出处）。

挑案例的原则：

- 覆盖不同类型的后续：临床读出（剂量、终点、样本量）、监管决定（受理、突破性疗法、批准与否）、交易与授权、指南或共识更新、更正与撤稿。
- 一段时间内报道很多的事件最能测出「新进展 vs 旧背景」有没有分开；只有一篇报道的事件用来测首次撰写。
- 案例别贪多。一次 6–10 个事件就够人工逐条读完；每多一个案例，每个模型和提示词各多一次调用。
- 案例里的事实和证据只放报道里真正有的内容。评测输入与线上完全一致（`buildStoryDigestInput`），案例里多写一句，评的就不是线上会看到的东西。

## 2. 并排对比

```bash
node --env-file=.env scripts/eval-story-digests.ts --cases .data/story-digest-cases.jsonl --system my-candidate.md
```

- 每个案例用现有提示词和候选提示词各跑一次：同一个模型（默认是「事件综述」这一步线上正在用的模型，`--models` 可指定），同一份输入，系统提示词、采样参数与线上生成时相同。
- 候选文件写法与 `industry/prompts/` 一致：`{{siteName}}` 换站名，`{{> 文件名}}` 插入共用规则，缺值会报错。候选渲染后与现有提示词完全相同会拒绝运行；不传 `--system` 就只跑现有提示词。
- 开始前打印调用次数（案例数 × 模型数 × 提示词数），超过 `--max-calls`（默认 18）一条都不发。每次调用照常记录、计入预算；原样重跑复用已有回执、不再付费，所以改一版候选再跑，现有提示词那一半不花钱。
- 结果写到 `.data/eval/`（`--out-dir` 可改），一份 JSON、一份 Markdown：两边的标题和综述并排，附每次调用的 token 用量和记录编号，失败的调用写明原因。并排报告是给人看的，不是分数。

## 3. 人工看什么

没有可靠的自动分数，这个工具也不让模型给模型打分。逐条看：

- 第一句是不是核心变化与当前结论；是不是在按日期复述下方时间线。
- 后续判断有没有分开：这次新给的数字、终点、适应证、监管阶段在前，旧背景在后；不要把上一版已经说过的事再讲一遍充数。早先与后续说法冲突时，有没有写完两种说法和各自的来源，而不是悄悄抹平。
- 限制条件有没有跟着对象走：剂量对应哪个人群、终点是主要还是次要、批准的是哪国监管、授权覆盖哪些地区。条件被抽走或挪到别的对象上，就是错的。
- 有没有报道和事实证据里没有的内容；有没有评论报道本身（「报道未披露……」）或把写作要求写进正文。
- 更正后重写时，失效的旧说法有没有清掉；撤稿或数据更正后，结论有没有跟着改。
- 标题是否不超过 30 字、概括整个事件，而不是复述最新一篇报道或第一句。

## 4. 改完提示词之后

提示词换版本不会重写已有事件的综述。事件只在报道变化时重新生成，有新报道时以旧综述为上一版增量改写，所以新提示词随新报道逐步生效，不会一次性产生大量模型调用。

想让某几个事件立刻用新提示词重写，在能连到数据库的环境里调用 `rewriteStoryDigest`（每个事件一次模型调用，记进后台审计）。数据库端口没有发布到宿主机，通常就在容器里跑：

```bash
docker compose exec api node --input-type=module -e '
const { rewriteStoryDigest } = await import("@aihot/backend/events/corrections");
const { sql } = await import("@aihot/backend/db");
const [s] = await sql`SELECT id FROM stories WHERE public_id = ${"<事件id>"}`;
if (!s) throw new Error("没有这个事件 id");
console.log(await rewriteStoryDigest(s.id, "综述提示词已更新", "ops-script"));
await sql.end();'
```

只在并排报告里确实看到改进时才换。换完把这一轮的报告留在 `.data/eval/`，下次改提示词先拿它当基线。
